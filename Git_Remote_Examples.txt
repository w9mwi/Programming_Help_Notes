A remote Git repository is usually located on a remote server.  However,
any repository that's not the one you're working from is considered
"remote", even if that other repository is located on your computer.

There are only 4 Git commands that communicate between a local Git repository
(located on your computer) and a remote Git repository.

1) git clone
2) git fetch
3) git pull
4) git push

All other Git commands work only on the repository you're working from.
This page covers these 4 Git commands.

========================================================================

GIT CODE COMMIT WORKLOW WHEN USING A REMOTE REPOSITORY
======================================================

The following 7 steps describe the typical Git workflow followed
by a developer in a software production environment.

Assume the production git repository is named Git_Prod and is located
on a remote server at this location:

https://github.com/w9mwi/Git_Prod

Assume your local git repository is named User_1 and is contained on
your local computer at this location:

/home/tjb/User_1 folder

The following 7 steps demonstrate the workflow of how a developer makes
code changes to the remote Git_Prod repository.

1) Fork the Git_Prod Repository on the Remote Server

   NOTE: On GitHub, a personal account cannot fork a repository that the same
         personal account already owns (forking requires copying from a different
         user or organization account). This step is included because forking from
         a shared repository into a personal fork is standard in a real-world
         software production environment.

   Using your web browser, navigate to and login to this web page:

   https://github.com/w9mwi/Git_Prod

   Fork this Git_Prod repository to a new repository named: w9mwi/User_1

2) Clone Your Fork to Your Local Computer

   From the /home/tjb folder on your local computer, run the following
   two commands, which will create a new folder named User_1.

   $ git clone git@github.com:w9mwi/User_1.git
   $ cd User_1

   Your fork (located on the remote server) now has the name "origin",
   and your local clone resides in your /home/tjb/User_1 folder.

3) Link Your Local Repository to Git_Prod (upstream)

   From your /home/tjb/User_1 folder, run this command.

   $ git remote add upstream git@github.com:w9mwi/Git_Prod.git

   NOTE: This command names the remote Git_Prod server "upstream".
         So now your local User_1 repository can communicate with
         the remote Git_Prod repository via the name "upstream",
         and with the remote User_1 repository via the name "origin".

4) Create the Name of the Release Branch and Make Code Changes

   The following command creates a new branch named Release_4 that's
   a copy of the "main" branch, and then switches your active branch
   to Release_4.

   $ git switch -c Release_4 main

   Make all your code changes on the Release_4 branch, and
   run the following commands.

   $ git add .
   $ git commit -m "Describe your code changes here"


5) Push Your Local Branch to Your Remote Fork Repository for Code Review

   From your /home/tjb/User_1 folder, run the following.
   
   $ git push -u origin Release_4

   From a web browser, navigate to your remote fork at:
   https://github.com/w9mwi/User_1

   Then click "New Pull Request" to request that the Git_Prod Maintainer
   review and merge your Release_4 branch into Git_Prod's main branch.
   (You don't run any commands directly on the Git_Prod remote repository.)

6) Sync Your Local Repository After Code Approval

   After the Maintainer approves and merges your Pull Request into the
   remote Git_Prod repository, update your local User_1 repository
   by running these 3 commands.

   $ git switch main
   $ git pull upstream main  (Update your local main branch from the remote Git_Prod repository.)
   $ git push origin main    (Upload your updated main branch to your remote fork User_1 repository.)

7) After your Release_4 changes are safely merged into the main branch, delete the old
   Release_4 branch locally and on your remote fork so your repository stays clean for
   future releases:

   $ git branch -d Release_4             # Delete the Release_4 branch from your local computer.
   $ git push origin --delete Release_4  # Delete the Release_4 branch from your remote fork (origin).

   Run the following commands to verify all is OK.

   $ git status
   $ git branch -a

GIT CLONE - Clones a remote Git repository to your local git repository/folder.

            NOTE - A remote repository is usually located on a remote server,
                   not on your local computer.  However, assume you have two Git
                   repositories on your local computer located in folders named
                   Repo_1 and Repo_2.  If you're currently working in the Repo_1
                   folder/repository, the Repo_2 folder/repository is considered
                   a remote repository from your Repo_1 folder/repository (and
                   vice-versa) even though they're both contained on your local
                   computer.  Therefore, you can clone a git repository from another
                   git repository on your local computer, or from a repository packaged
                   within a Git ".bundle" archive file.

            Git translates a "git clone" command into 5 separate commands.  For example,
            Git translates the following command into the 5 commands below it.
            $ git clone git@github.com:w9mwi/My_Git_Repo.git

            $ mkdir My_Git_Repo
            $ cd My_Git_Repo
            $ git init
            $ git remote add origin git@github.com:w9mwi/My_Git_Repo.git
            $ git pull origin main

            If the remote repo is named iwm9w/My_Git_Repo and is located on bitbucket.org,
            replace the two similar commands above with these two commands:
            $ git clone git@ssh.bitbucket.org:iwm9w/My_Git_Repo.git
            $ git remote add origin git@github.org:iwm9w/My_Git_Repo.git

            If you want the cloned repository to exist in a folder having a different
            name (i.e., /home/tjb/My_Cloned_Repo), run the following command instead.

            $ git clone git@github.com:w9mwi/My_Git_Repo.git  My_Cloned_Repo

            To be safe, make certain the folder in your local directory that will hold
            the cloned repository (i.e., /home/tjb/My_Git_Repo) either doesn't exist,
            or it is empty.

            By default, Git clones only the repository's default branch, which is usually
            named "main" or "master"--it doesn't clone any other branches.  To clone a
            different branch from a remote repository specify the -b flag, followed by
            the branch name as in the following command.

            $ git clone -b branchName git@github.com:w9mwi/My_Git_Repo.git

            Running this command will also designate "origin" as the branch name you cloned.
            Therefore, when you run the the "git fetch", "git pull", or "git push" commands
            later, they will work without having to specify a branch name in those commands.
            However, if you create a new branch on your local computer named "newFeature_1",
            you will need to run the following command for it to appear on the remote repository.

            $ git push -u origin new-feature

            The -u flag permanently links the connection between your local main
            branch and the remote "origin/main" branch so the next time you need
            to run the "git push", "git fetch" of "git pull" command, you can just
            run "git push" without specifying any flags or arguments.

            If you need only the latest version of the code, instead of a history of every
            commit made, you can save time and disk space by running a "shallow clone".
            To do that specify the --depth flag as in the following command.

            git clone --depth 1 git@github.com:w9mwi/My_Git_Repo.git

            The "--depth 1" flag downloads only the single most recent
            commit instead of the entire project history.

CREATE A NEW REMOTE GIT REPOSITORY
==================================
You can create a new remote git repository on github.com or bitbucket.org
via a web browser.  You can also create a new remote git repository on
github.com or bitbucket.org from the command line on your local computer
by using the Linux "curl" command.

This tutorial only covers creating a new remote git repository via
a web browser.


1) Navigate to your user account on github.com or bitbucket.org via
   a web browser and create a new reposirory named My_Git_Repo and
   leave it empty.

2) On your local computer, open a command-line console window and create
   a new folder named "My_Git_Repo".  Next, navigate into the My_Git_Repo
   folder and run the following command.
   $ git init -b main   ("-b main" creates a git branch named "main")

   Confirm the above command created a ".git" folder within the My_Git_Repo folder.

3) Create some files that will reside in your My_Git_Repo folder.  Then,
   add and commit those files into your local repository by running the
   following commands.
   $ git add .
   $ git commit -m "A comment describing the new files committed."
   $ git status  (Confirm it returns the following 2 lines of text.)
   On branch main
   nothing to commit, working tree clean

4) Run the following command.
   $ git remote add origin git@github.com:w9mwi/My_Git_Repo.git

   NOTE: If the git repository is located on bitbucket.org, use this command instead.
         $ git remote add origin git@ssh.bitbucket.org:iwm9w/My_Git_Repo.git

   The above command updates the hidden file .git/config  inside the My_Git_Repo folder.
   It does not connect to the internet or transfer any data.

5) Run the following command:
   $ git push -u origin main

   This command uploads your local commits from the main branch to the remote repository
   nicknamed "origin", and permanently links the two branches together.  Once this command
   finishes, your files and commit history will appear in the remote My_Git_Repo repository
   located on the github.com server.

   In the above "git push" command...
   * "origin" designates the nickname you of the remote server.
   * "main" designates the branch pushed to the remote github server.
   * The -u flag permanently links the connection between your local main
     branch and the remote "origin/main" branch so the next time you need
     to run the "git push", "git fetch" of "git pull" command, you can just
     run "git push" without specifying any flags or arguments.

   The following command prints the names od all remote repositories,
   returning text similar to what appears below.
   $ git remote -v
     central_repo git@github.com:w9mwi/central_repo.git (fetch)
     central_repo git@github.com:w9mwi/central_repo.git (push)
     my-git-repo  git@ssh.bitbucket.org:iwm9w/my-git-repo.git (fetch)
     my-git-repo  git@ssh.bitbucket.org:iwm9w/my-git-repo.git (push)
     origin       git@bitbucket.org:iwm9w/my-git-repo.git (fetch)
     origin       git@bitbucket.org:iwm9w/my-git-repo.git (push)
     origin_2     git@github.com:w9mwi/central_repo.git (fetch)
     origin_2     git@github.com:w9mwi/central_repo.git (push)

GIT PULL - NOTE: Each developer on a team has a local git repository on their
                 local computer, and a "forked" repository that resides on the
                 same remote git repository as the production repository.  Each
                 developers' local repository and "forked" repository were both
                 originally a clone of the production repository.  After a
                 developer pushes her code changes to her remote "forked"
                 repository for review, the team leader reviews that code.
                 If the team leader approves those code changes, she pushes it
                 (using "git push") to the remote production repository.

           The "git pull" command is typically run in a developer's local repository
           only after she has completed all of the following.

           * Finished the task she's working on.  Such as fixing bugs, adding new
             features, or making other change(s) to her local repository.
           * Has completed testing all changes made in her local repository.
           * Has run "git add" and "git commit" on all files changed.
           * Has successfully pushed those local repository changes to her
             remote "forked" repository via the "git push" command.
           * The "Code Maintainer", "Team Lead", or "Release Manager" has
             approved those code changes by pulling them from the developers
             remote "forked" repository into the remote production repository
             using the "git pull" command.

           After all of the above is finished, the developer runs the "git pull"
           command from her local repository so it gets updated with all changes
           made to the remote production repository (by other developers) since
           the last time she ran "git pull" from her local repository.

           WARNING:  Running the "git pull" command from you local repository
                     can be dangerous because it changes the contents of your
                     local repository.  So if you made a mistake running that
                     command, it can be difficult to fix.  Instead, it's safer
                     to run "git fetch' from the remote production repository
                     to first inspect the files it has changed.  (The "git fetch"
                     command doesn't change any files in your repository, it
                     only allows you to see pending changes.)  After confirming
                     that "git fetch" has changed the appropriate files, run
                     the "git merge" command to force those changes into your
                     local repository.  The "git pull" command is equivalent
                     to running "git fetch" followed by "git merge".

GIT MERGE - The following 7 steps demonstrate the process of code development.  Once
            you understand this process you will understand what the "git merge"
            command does, and exactly when you need to run it.

           1) Assume you already have a working directory in your local repository
              that's a copy of a branch that was checked out, or cloned, from a remote
              repository.  And now you want to add a feature, fix a bug, or make some
              other code changes on that branch.  Assume the remote repository is named
              "origin" and the branch is named "main".  Follow the next 6 steps.

           2) Run "git add" and "git commit" as needed.
              As you make code changes, you must execute both the "git add" and
              "git commit" commands on files when needed.

              After running your final "git add" and "git commit", you will be finished
              making all your code changes.  So you should now test all your code changes.
              Once your code has passed testing, proceed to step 3).

           3) Run "git status"
              Confirm "git status" returns the following text:
              "nothing to commit, working tree clean."

           4) Run "git fetch" 
              It probably took several hours or days to finish making and testing your code
              changes.  After you're finished testing, you must again run "git fetch" on that
              same remote repository branch.  Doing so will obtain any code changes made
              by other developers since the main branch was originally cloned or checked
              out in step 1) above.

           5) Run "git merge origin/main" immediately after running "git fetch" in step 4) above.
              If you and another developer edited the same line of text in the same file, Git will
              prompt you to resolve any merge conflicts.  If there are merge conflicts, you
              must resolve them and once again run "git add" and "git commit" on every file that
              you changed.

              NOTE: You can run the "git pull origin/main" command in place of "git fetch"
                    in step 4) and "git merge" in step 5) because "git pull" combines
                    both those git commands.  However, it's safer to run "git fetch"
                    followed by "git merge" because "git fetch" allows you to review
                    files before you merge them.  Using "git pull" can also force you
                    to resolve complex merge conflicts in the middle of your workflow.
                    Etc.

           6) If you had to resolve merge conflicts in step 5) above, run "git status"
              again to confirm it returns the following text:
              "nothing to commit, working tree clean."  

           7) Run "git push" so all your code changes get sent to the remote repository,
              which is used to build the production release.
